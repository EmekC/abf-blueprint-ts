# abfc roadmap

Sizes are rough estimates for one developer: S is under 1 week, M is 1 to 3 weeks, L is 3 to 6 weeks. Each phase ends with a tagged commit. Design references point to `docs/design.md`.

## Phase 1: milestone 1, one real mod slice (L)

Scope
- Monorepo skeleton: `@abfc/runtime`, `ir`, `env`, `compiler`, `backend`, `stubgen`, `testkit`, `cli`. Node 24 pinned, exact TS, `node:test`.
- `@abfc/env`: full precedence chain, Known Folder Documents lookup, Epic manifest discovery, Python discovery, headless-dir space check, the error shape from design 9.3, and `abfc doctor`.
- Backend: `backend_info` and `reflect`, plus `compileErrorNodeRefs` if it is small, all in `EmekC/abf-mod-editor-mcp`. The MCP stdio client and the bp_apply adapter with capability gating.
- Backend, from Phase 0 probe P5 (failed, also seen in P3 and P6): native node kinds `array_call`, `break_struct`, `make_struct`, plus explicit pin-type resolution for every wildcard-capable node (array functions, `GetArrayItem`, `cast` with its `Object` pin, and later `Map_*`, `Select`, `MakeArray`, macros). `k:"node"` and native `cast` leave wildcard pins undetermined and the build fails. Until these land, the adapter may use the two-phase route proven in Phase 0 (apply, read the rolled-back `final_0.t3d`, patch the pins, apply the graph as `raw`), but it should resolve types up front because a failed first apply adds 10 to 20 s.
- `abfc stubs` for the two `/Game` classes, their `/Script` closure, and the mod's own assets (`_Manual` interfaces). Stub lock and version-mismatch errors.
- Compiler: the TS subset needed for `UpdateTarget` (casts, `?.`, `&&`, `===`, ExpandEnumAsExecs results, `for..of`, struct breaks, temps), passes 1 to 3 and 6, manifest, drift check, `abfc adopt`, source map.
- `abfc check`, `build`, `test` (testkit with `spawn`, `call`, `get`, `wait`, `expect`), `status`.
- Map and struct probes from Phase 0 stay as probes. Their results only set capability flags (both false until a stage audit passes; compile and game test passed, see Phase 4).

Exit criteria
- A TS project for a real mod (outside the mod folder) holds `UpdateTarget` in TS. `abfc build` adopts and replaces the hand-made event, compiles clean, and passes the existing relay game test plus the new `UpdateTarget` tests, all from a plain terminal with no MCP client.
- Editing a generated node in the editor makes the next build fail with ABFC5001, and nothing is overwritten.
- A deliberate type error and a deliberate Unreal compile error both show up at the correct `file.ts:line:col` in VS Code's Problems panel.
- `abfc doctor` passes on a second Windows account whose user name contains a space and whose Documents folder is redirected. The doctor prints the headless-dir advice and the build works after following it.
- A changed editor fingerprint (simulated) triggers ABFC3001.
- Build timings recorded. Nothing published to the real mod unless the user runs `abfc publish` (the gate is a stub in Phase 1: build plus test plus `mod_audit` plus dry-run only).

## Phase 3: widgets, hybrid mode (M)

Scope: `kind: "widget"` classes, `_Manual` stubs exposing designer widgets, owned graphs inside a mod's widgets (for example `WBP_PotInfo` and `WBP_PotInfoBuffLine`) with the layout untouched, `create_widget`, and `liveHud` test marking with a manual checklist report.
Exit: The real mod's widget logic in TS, layout unchanged byte-for-byte outside owned graphs (checked by export diff), hidden tests pass, and the manual HUD check passes in PIE.

Result (2026-11-07): The test mod's two widgets now have their logic in TS: 4 widget events were ported and are owned (the old hand-made nodes were removed with `adopt --remove-node`), plus 13 relay and director units that were moved to call the TS widget classes. A live `abfc publish` exits 0 (publish.total 23.7 s) without ABFC7013. Layout evidence uses `scripts/layout-diff.mjs` on exports from before and after the port: the normalized comparison (against the pre-port baseline; the same multiset of byte-identical sibling blocks) and `--strict` (against a baseline exported after a reload, raw order) both print "layout identical" for both widgets. The hidden widget tests pass (two tests for the buff-line setter, two for the info display, and the injection test including child rotation and slot properties). The manual PIE HUD check is pending (the user runs `.abfc/reports/manual-checks.md`, written from the `test.liveHud` tests), so the exit criterion is Partial until then. Added this phase: `test.liveHud` with the manual-checks report; `ABFC6105`; retire of fully deleted classes (`retiredUnpublished`, `ABFC5010`); TS `@blueprint` classes as types, in `createWidget` and for calls to their `@event`s; `x as T` only where the Blueprint type does not change (no node; otherwise `ABFC2099`, also for `as const`); built-in stub supplements (`Slot: PanelSlot | null`, readonly, on `/Script/UMG.Widget`; STUBGEN 0.2.1) and `stubs.widgetMembers` for base-game widgets; `parseExport` keeps plain node keys for the EventGraph and prefixes colliding nodes of other graphs with `<graph>/` (fixes an adoption hash mismatch between warm and cold exports). Backend work stays on the uncommitted branch `abfc-p3-live-reload` (awaiting review): transitive, dependency-ordered reload of referencers, an in-memory recompile of Blueprints that logged transient errors during the reload, and `set_default` writing `DefaultTextValue=NSLOCTEXT(...)` for text pins (without it a Format Text output is empty at runtime). Until a backend has that branch, Format Text output would be empty and widget publishes can print `ABFC7013`. Known gaps: `continue` and array literals are `ABFC2099`; there is no force-rebuild flag (a unit is re-planned only when its IR hash changes); no-substitution template literals are not accepted as text (use string literals); Git Bash needs `MSYS_NO_PATHCONV=1` for `/Mod/...` arguments.

## Phase 4: maps, sets and structs (M, depends on P6 and P7)

Scope: native `Map` (not `Set`) if the P6 audit criterion passes (backend type grammar extended in `EmekC/abf-mod-editor-mcp` from the Phase 0 patch (in git history at commit `8278ba6`, path `spike/backend-p6-map.patch`), plus wildcard-pin resolution for `Map_*` nodes); P6 compile and game test passed in Phase 0, the audit was not verified. If a later audit of the stage fails, parallel-array lowering with `Array_Find` and the capability stays false. Set not probed in Phase 0; native Set needs a `set:` grammar probe, else parallel-array lowering. `@struct` classes as UserDefinedStruct if the P7 audit criterion passes (compile and game test passed in Phase 0, the audit was not verified); this also needs a backend extension for field authoring, since Python in this build can create the struct but not set its fields, and mod struct variable types use the full object path (`.../S_Probe.S_Probe`). If the audit fails, `@struct` is dropped and ABFC2045 explains why.
Exit: a sample mod using a `Map<name,int>` and one struct builds, tests and passes `mod_audit`. Unsupported combinations fail with an ABFC error before launch.

Result (2026-11-07): Probes in a staged copy: Map (`map:name:int`), Set (new backend `set:` grammar) and UserDefinedStruct each apply, compile clean and pass a game test. The six untried Map/Set pin names (Map_Remove, Map_Clear, Map_Contains, Map_Length, Set_Remove, Set_Clear) were verified live. Struct field authoring: Python in this build cannot set struct fields directly, so the backend writes `VariablesDescriptions` on a throwaway UserDefinedStruct and duplicates it to the final path (the duplicate is compiled by the engine; an in-place swap is not). This was verified by reflect (Break pins `<Field>_<i>_<GUID>`) and by game tests. Changing the fields of an existing struct is refused (ABFC2046 in abfc, an error in the backend); it needs a trusted delete plus recompiling the referencers, and is deferred. abfc now has own fields `Name!: T;` (ABFC2047), create-if-missing for new assets (ABFC2044 when the backend cannot create the kind), native `Map`/`Set` on own fields (ABFC2040/2042/2043), `@struct` classes (ABFC2046) and a feature gate before launch (ABFC2044). The capabilities `map`, `set` and `struct` are on by policy, with the stage audit pending. Sample: a TS class with a `Map<name,int>`, a `Set<name>` and one `@struct` builds (build.total 18.0 s cold-ish, 12.2 s for a warm gate build), compiles clean, and its 3 game tests pass. `abfc publish --full`: gates 1 to 4 pass (17/17 tests, after fixing the test mod's own Director test, which still called a renamed function); gate 5 (stage `mod_audit`) fails with `ABFC7002` because the audit's hidden Mod Editor shows only an Epic "Logging In" window and never mounts the mod (4 attempts today; it worked in Phases 2 and 3). The backend now fails fast: the audit stops after `ABF_LOGIN_GRACE` (60 s) with a clear error instead of a 300 s timeout. Nothing was published. Exit criteria: builds and tests met; passes `mod_audit` UNMET (pending the Epic login); unsupported combinations fail with an ABFC error before launch met (8 negative checks fail at the frontend in 0.4 s; against a backend without the features, `ABFC2044` before staging). Backend work (set grammar, struct creation with `struct_fields`, login fail-fast; 215 unit tests) was merged into the backend's main branch as EmekC/abf-mod-editor-mcp#6 (d1356de). The fallback branches (parallel arrays, dropping `@struct`) were not needed and were not built; if a later stage audit rejects maps, sets or structs, the capability policy flips to false.

## Phase 5: language service and lint polish (M)

Scope: `@abfc/ts-plugin` (subset diagnostics, hover showing the Blueprint node a line lowers to, quick fixes for `idiv` and `?.`), and `@abfc/eslint-plugin` rules: no heavy calls in tick (`GetAllWidgetsOfClass` and friends), replicated-variable writes without an authority check, RPC misuse, loops in tick, unbounded array growth. Watch mode for `abfc check`. Stub hover text: every callable function in the generated `.d.ts` stubs (game, engine and mod classes) carries a short, precise one-line description followed in parentheses by the node's display name in the Blueprint node editor, e.g. `K2_GetPawn` gives "Returns the pawn this controller possesses (Get Controlled Pawn).", shown by VS Code on hover and in completion. Phase 0 found that the cooked Mod Editor strips function metadata (tooltips, display names) through the Python routes tried, so the text comes from (a) a backend probe for a metadata route that works, for example reading the title and tooltip of a spawned K2 node, which `reflect` already creates for pin materialization (see Phase 6), or otherwise (b) the display name derived by Unreal's own naming rule (strip `K2_`, split camelCase) plus a curated description file kept in the repo for the common classes, with no Deep Field-derived text copied verbatim. Your own doc comments: a TS `/** ... */` comment on an `@event` or function member becomes the tooltip of that Blueprint function or event in the editor, plus category and keywords if feasible, through the Phase 6 `bp_apply` metadata extension.
Exit: rules documented with examples, no false positives on the test corpus, and the plugin gives the same diagnostics as `abfc check` on the full test corpus. Every stubbed function in the test corpus has a one-line description with its node-editor name in parentheses, and a TS doc comment shows as the tooltip of its Blueprint function or event in the editor.

Result (2026-11-07): Phase 5 is implemented; one exit criterion is pending a manual check. (1) Rules documented with examples: met. `docs/lint-rules.md` documents the 5 rules of `@abfc/eslint-plugin` with bad and good examples. (2) No false positives on the test corpus: met for the rules the corpus can exercise. `scripts/lint-corpus.mjs` gives 0 findings on the test project (10 files) and on the compiler fixtures project, phase2 and phase3; fixture phase4 gives 1 finding (`no-unbounded-array-growth`, `Fields.ts`), reviewed as a true positive. The test corpus's own assets have no replicated variables and no net events, so `replicated-write-needs-authority` and `rpc-misuse` have no corpus data: they are covered by RuleTester cases and a scratch positive control only. The tick rules are lexical and do not follow calls, by design. (3) Plugin diagnostics equal `abfc check`: met. `scripts/plugin-parity.mjs` exits 0 with 0 mismatches on the 4 compiler fixtures (12 to 22 diagnostics each) and on the test project; the test project itself has 0 diagnostics, so its parity is trivially equal. Parity excludes the lock codes ABFC3001 to ABFC3003, ABFC2000, spanless diagnostics and TypeScript's global diagnostics (they need the installed Mod Editor or a position). (4) Stub descriptions: met in form on the test corpus; 3 game-module functions have only the generic `Calls X.Y (Name).` text. All 34 stub functions the corpus calls have a one-line description ending in `(<Node Name>)` (`scripts/stub-desc-coverage.mjs` exits 0): 31 curated engine functions, and 3 game-module functions that the shipped table deliberately does not name, which show the fallback `Calls X.Y (Name).` with the reflected display name because the editor carries no tooltip for them; other functions use the tooltip reflected from the editor, or the fallback (827 of 3129 members in the corpus profile). Display names come from a backend metadata probe (`EditorAssetLibrary.get_metadata_tag`, `ToolTip` and `DisplayName` of `/Script` UFunctions) with the `displayNameOf` rule as fallback. The coverage script does not pass on the 4 compiler fixtures, which use hand-written fake stubs without description lines. (5) Doc comment as Blueprint tooltip: met for events, unmet for functions; for events it is met in the stage export and unmet visually until the user checks. The probe found that a `FunctionMetaData` line is dropped on import and that compiled Blueprint function metadata cannot be read back through Python, while an event node's `MetaData=(ToolTip=...,Category=...,Keywords=...)` survives import and export. So the backend `bp_apply` gained event-node metadata (feature `event_meta`: the Phase 6 "function and event metadata" item, done early, events only; function graphs are not covered) and abfc writes the `@event` doc comment, `@category` and `@keywords` through it; a backend without `event_meta` gets warning ABFC2071, and the unit cache records per documented event whether the tooltip was written, so the next build after a backend update applies those events again by itself. After `abfc publish` (not `--full`) into the test mod, all 16 documented `@event`s show `MetaData=(ToolTip=NSLOCTEXT(...))` on their custom-event node in the stage export. Seeing the tooltip on hover in the Mod Editor is a manual check (no UI automation is allowed) and is pending user confirmation; the steps are in the test project's `.abfc/reports/manual-checks.md`. (6) `abfc check --watch`: met; a re-run after a save takes 0.3 to 0.5 s on the test project (target under 2 s). Also added: the `idiv` intrinsic (`Divide_IntInt`) with the ABFC2010 quick fix, the `@bpReplicated`, `@bpRpc` and `@bpReliable` stub tags (stubgen 0.3.0), and the Phase 4 stale sentence fix. Backend work is on the uncommitted branch `abfc-p5-metadata` (its own worktree), to be opened as a PR. Known limits and issues: the plugin needs the workspace TypeScript 6.0.3 (`typescript.tsdk`; VS Code's bundled TypeScript and TS 7 do not load it); VS Code may not request the ABFC quick fix when it asks for supported fixes without a file (the `?.` fix is unaffected); the replication and RPC rules see hand-made members only (TS-side `@replicated` and `@event` net options are not a feature yet); `abfc check` does not run ESLint; an intermittent ABFC4002 access violation was seen once during the `abfc stubs` reflect (the chunk retry succeeded); `abfc publish --full` still fails at gate 5 (ABFC7002, the Epic login chooser), which is unrelated and open. Two Phase 2 carry-overs, a restore after a post-apply compile failure and an opt-in drift read for unchanged builds, remain out of scope and move on.

## Phase 7: public release 1.0 (M)

Carry-overs from Phases 2, 5 and 6: function locals (backend and lowering), changing the fields of an existing struct, `classManagerRow` row writing, the `no-unbounded-array-growth` false positive on one-time setup pushes, `rpc-misuse` flagging calls inside server RPCs, restore after a post-apply compile failure, the opt-in drift read for unchanged builds, the ABFC4012 code collision, and `abfc publish --full` gate 5 (ABFC7002 Epic login) if still open.

Scope: docs (install, first mod, CLI reference, error code reference, backend setup, troubleshooting for OneDrive, spaces and non-English Windows, the SmartScreen warning), the `abfc init` command and its templates, a single-file `abfc.exe` and installer, `abfc lsp`, the derived asset path model, npm publishing with provenance, semver, changelog, GitHub releases, and release hygiene checks (below). The separate `abfc backend install` step is dropped: the backend ships inside the release. The sha256-pinned backend download stays only for source installs, if it is still needed.
Exit: a stranger on a clean Windows machine with only the Mod Editor goes from the installer (or the zip) and `abfc init` to a build and a publish to staging, by following the docs, with no mod name or path hardcoded in TS source.

The live publish was refused by the open editor (ABFC7005) because one asset had unsaved changes in the editor: the user must save or revert it in the Mod Editor, then publish. Issues found and fixed during the live checks: ABFC5012 now matches moved classes by class name before file; removing `@director` leaves a stale class-manager row, which is now cleared from the manifest with a warning (ABFC5013); stubs no longer warn on non-Blueprint assets. Remaining: the minimum backend stays 2.4.0, and rows need 2.5.0 (merge and tag pending).

Decisions (2026-11-07):

Distribution: one `abfc.exe` (Node single-executable) that bundles the pinned backend and an embeddable Python. The only prerequisite is the Mod Editor. The source stays installable and usable directly (npm or git). The installer is classic: plain, simple, predictable. An update is running the newer installer. There is no code signing; the docs explain the SmartScreen warning.

`abfc init`: it detects the Mod Editor install and its mods folder, scans the mods folder and lists the available mods. The user can change the mods folder and rescan. It links exactly one existing mod; it does not create a mod. One mod per TS project. It writes a project config that names the mod (safe to commit, no absolute paths) and a per-machine user config with the absolute paths (editor install, mods folder). It generates tsconfig, a sample class, `.gitignore` and editor settings, runs `abfc stubs` (stubs are generated locally and never shipped), and ends with a `doctor` checklist. The non-interactive form is `abfc init --mod MyMod --yes`.

Language support: `abfc lsp` is a standard stdio language server in the same executable (diagnostics, hover with node names, quick fixes, the lint rules) for any LSP editor (nvim, Helix, Zed, JetBrains). For VS Code, a small extension ships as a `.vsix` inside the release zip and the installer installs it. It is not published on the marketplace. Whether the current tsserver plugin is kept or retired is decided during Phase 7.

Project model: the asset path is derived, not hardcoded. It is `/<mod>/` from the project config, plus the folder of the TS file relative to `src/`, plus the class name. Example: `src/Relays/MyCustomRelay.ts` with `class MyCustomRelay` gives `/<mod>/Relays/MyCustomRelay`. `@blueprint()` needs no arguments in the common case. `path:` stays as an optional override (for example to adopt an existing asset elsewhere, or in hybrid mode). Existing explicit `path:` values keep working, and a quick fix drops one that equals the derived path. The class-manager row moves to a separate decorator, `@director("RowName")`. The class-manager table path comes from the project config (default `/<mod>/DataTables/DT_ClassManager`). This is where the `classManagerRow` row-writing carry-over lands. abfc records each asset's path on its first build. If a later build finds the TS file moved or renamed, it stops with a clear ABFC error that offers two ways out: (a) keep the old asset path, through a quick fix that adds `path:`, or (b) `abfc mv`, which moves the asset in Unreal and fixes references. Option (b) is built only if a backend probe shows it works headlessly. Folder and class names are checked against characters Unreal does not allow. Switching the target mod (for example a test mod and the real mod) is one config value, and no mod name appears in TS source.

Sub-milestones (specification in design section 18): 7a project model (derived paths, `@mod/` imports, schema-2 config and user config, `@director` with class-manager row writing in backend 2.5.0, moved-file error ABFC5012, `abfc init`, the row and headless-move probes); 7b `abfc lsp` and the VS Code `.vsix`, tsserver plugin retired; 7c `abfc.exe` with the bundled backend and embeddable Python, Inno Setup installer and zip; 7d release hygiene CI, npm with provenance, docs set, the remaining carry-overs (design 18.12; function locals and changing struct fields are deferred after 1.0), `abfc mv` only if the probe passed, and the clean-machine exit walkthrough.

Release hygiene: release artifacts (exe, zip, installer, npm packages, `.vsix`) are built from an allowlist. CI scans the built artifacts, not only the repo, for mod names, user paths and game-derived files, and fails the release on a hit. This replaces and widens the earlier check for stub headers and `/Game` reflection JSON. Tests, scripts, plans and internal docs never ship. Mod names are being removed from the backend tests and from the git history of both repos (in progress).
